# AIGC 检测反制通用规则 (Shared Anti-AIGC Rules)

所有输出类技能继承此文件的通用反 AIGC 规则。各技能在 `rules/anti-aigc.md` 中扩展领域专属反制规则。

---

## 核心原则

输出文本反 AIGC 的关键是**具体、有决策理由、有边界**。AI 倾向生成正确的但可以放在任何项目里的泛泛之谈。人类写的文字会有具体数字、折衷选择、明确的不确定标注。

## 通用 AIGC 高发模式

### 1. 万能形容词（权重30%）

```
❌ AI 模式：
"功能强大"、"全面支持"、"智能高效"、"便捷灵活"、"性能优异"
→ 这些词可以套在任何内容上，毫无区分度。

✓ 人类写法：
用具体行为/数字/限制替代形容词。
"支持 JSON/YAML/TOML 三种格式"而非"支持多种格式"
"p50 < 50ms"而非"性能优异"
```

### 2. 机械递进（权重25%）

```
❌ AI 模式：
"首先...其次...再次...最后..."
"第一...第二...第三..."
→ 高度可预测的递进结构，AIGC 检测器权重极高。

✓ 人类写法：
用数据流关系、依赖关系、时间顺序等自然逻辑连接。
不用标记词，用内容本身的逻辑流动。
```

### 3. 空洞泛化（权重20%）

```
❌ AI 模式：
"可以满足多种场景需求"
"适用于各类项目"
"具有较好的可扩展性"
→ 没有具体场景，没有具体约束。

✓ 人类写法：
"适用于单机百万级记录，不适合分布式集群（需额外3天开发）"
```

### 4. 全确定语气（权重15%）

```
❌ AI 模式：
全文语气确定，所有决策像唯一正确答案。

✓ 人类写法：
"此处有折衷"、"以下两方案均可，选A因为X，后续可能需要切换为B"
"不确定Z的影响，需后续验证"
```

### 5. 无排除理由（权重10%）

```
❌ AI 模式：
"选用 PostgreSQL"
→ 为什么不是 MySQL？为什么不是 SQLite？

✓ 人类写法：
"选用 PostgreSQL 而非 MySQL，因为需要 JSONB 字段和事务性 DDL。
排除 SQLite 因为需要并发写入支持。"
```

## 五原则速查

| 原则 | 不写 | 写 |
|------|------|-----|
| 边界优先 | "全面支持X" | "支持X（限制：Y），不支持Z" |
| 数字优先 | "性能好" | "p50 < 50ms, p99 < 200ms" |
| 理由优先 | "选用A" | "选用A因为[具体理由]，排除B因为[具体理由]" |
| 折衷标注 | 全确定语气 | "此处有折衷"、"需后续验证" |
| 打破递进 | "首先其次最后" | 用依赖关系、数据流等自然逻辑 |

## AIGC 率评分标准

- 0-15%：人类专家撰写，有具体数字/折衷/限制
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，像模板填空
- 51-70%：需重写，空洞无实质
- 71-100%：纯 AI 模板

## 技能专用扩展

各技能在自身 `rules/anti-aigc.md` 中扩展：
- **技术文档类** (master-architect, python-project-developer, software-planner)：技术选型、架构描述、规格参数
- **学术论文类** (academic-writer, patent-writer)：学术语言模式、引用规范、公式描述
- **技能文档类** (skill-manager, skill-refiner)：技能描述、功能列表、命令说明
- **写作类** (humanizer, literary-ghostwriter, brief-write, official-document-writer)：文体模仿、领域术语
