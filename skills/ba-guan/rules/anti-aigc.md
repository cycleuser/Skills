# 分析报告反AIGC检测规则

分析类报告（代码审查、项目分析、安全审计等）的AIGC检测重在**证据**和**判断**。AI报告的特征是罗列但无判断，数据但无洞见。

## 核心原则

分析报告的价值不是信息罗列（AI最擅长这个），而是从信息中提炼出有判断力的结论。好的分析报告读完后，读者知道"该怎么办"。AI报告读完后，读者只知道"有问题"但不知道"具体什么问题、多严重、怎么修"。

## 分析报告AIGC高发模式

### 1. 列表罗列无优先级（权重30%）

```
❌ AI模式：
以下是发现的问题：
- 代码风格不一致
- 缺少单元测试
- 性能可以优化
- 文档需要补充
- 安全漏洞存在
（5个问题看起来同样重要）

✅ 专业写法：
P0 - 必须修复（阻塞发布）：
  · /auth/login 存在SQL注入，攻击者可绕过认证——这会在24小时内被扫描器发现

P1 - 应该修复（发布前）：
  · 3个核心模块缺少单元测试，覆盖率仅12%
  · /api/users 端点没有分页，1万条记录时响应18s

P2 - 建议修复（下一版）：
  · 代码风格用ruff统一，当前14处不一致
  · README的Python版本要求写的是3.8+但实际用了3.10的match语法
```

### 2. 数据罗列无洞见（权重25%）

```
❌ AI模式：
"代码共有142个文件，3521行代码，测试覆盖率47%。"

✅ 专业写法：
"测试覆盖率47%，但分布极不均：core模块0%（532行无测试），api模块82%。这意味着最核心的数据处理逻辑反而没有测试保护——如果发布后core出bug，排查成本最高。"
```

### 3. 审查意见笼统（权重20%）

```
❌ AI模式：
"建议改进代码质量"
"建议增加测试覆盖"
"建议优化性能"
"建议完善文档"

✅ 专业写法：
"core/aggregate.py:47 的 for 循环处理10万行CSV时耗时4.2s，改为pandas.groupby后降到0.3s（测试数据见bench/results.csv）。但注意pandas会多占50MB内存，内存受限环境需用生成器方案。"
```

### 4. 审查报告中立到无意义（权重15%）

```
❌ AI模式：
"代码总体质量良好，但仍有一些改进空间。"
"测试覆盖率有待提高。"
"安全方面需要关注。"

✅ 专业写法：
"代码能跑，但3个地方会在生产环境出问题：
1. SQL注入（/auth/login，P0，必须修了再上线）
2. 内存泄漏（长连接场景，P1，一周内修）
3. 日志里明文打印了API key（security/log.py:23，P0，今天修）"
```

### 5. 审查报告格式过度精美（权重10%）

```
❌ AI报告特征：
- 大量emoji和图标装饰
- 每个section结构完全对称
- 加粗格式："**问题**：XXX"
- 每个问题都有"**建议**：XXX"

✅ 专业报告：
- 文字为主，仅在必要时加粗关键数字
- 结构按优先级而非按类别组织
- 建议"可操作"而非"笼统建议改进"
- 写明谁负责修、什么时间前修完
```

## 反AIGC五原则

### 1. 优先级明确

P0/P1/P2分级，不是所有问题都"值得关注"。

### 2. 证据具体

每个判断附上文件路径、行号、数据、复现步骤。

### 3. 判断有力

不写"需要关注"，写"会在生产环境出问题"。

### 4. 建议可操作

不写"建议优化"，写"改为pandas.groupby，注意多50MB内存"。

### 5. 打破对称

重要问题5段话，次要问题1句带过。不要每个问题都3段话。

## AIGC率检测清单

- [ ] 是否有P0/P1/P2优先级划分？→无=AI
- [ ] 每个问题是否有文件路径+行号？→无=AI
- [ ] 是否有可操作的修复建议？→笼统建议=AI
- [ ] 格式是否过度精美？→过多bold/emoji=AI
- [ ] 重要和次要问题篇幅是否区分？→均匀=AI

### AIGC率评分标准

- 0-15%：优秀分析，读后知道怎么办
- 16-30%：合格，有洞见但少量空洞
- 31-50%：需要修改，信息罗列无判断
- 51-70%：需要重写，全篇套话
- 71-100%：纯AI模板报告
