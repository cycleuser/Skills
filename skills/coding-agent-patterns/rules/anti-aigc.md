# 代码架构文档反AIGC检测规则

代码架构模式文档（agent循环设计、上下文管理、工具安全、多模型抽象）面临独特的AIGC风险——它描述的是工程师设计决策，容易被写成正确的但放在任何agent框架都成立的泛泛之谈。好的架构文档读起来像架构师在白板前讲解"为什么这么做"；AI生成的读起来像设计模式的教科书记忆，空有术语没有取舍。

## 核心原则

代码架构文档反AIGC的关键是**决策理由充分**和**有取舍分析**。AI倾向生成"采用X模式"后列出X模式的一般性优点，而非针对本agent的约束。人类写架构文档会写"为什么选这个而非那个"，会写具体的token数、延迟ms、内存MB等量化约束。

## 代码架构文档AIGC高发模式

### 1. 模式描述空洞（权重25%）

```
❌ AI模式：
"使用上下文管理进行压缩"
"采用安全层级模式"
"实现多模型抽象层"
"采用循环检测机制"

问题：这些描述放在任何agent框架都成立，没有具体实现细节。

✅ 专业写法：
"上下文压缩策略：保留最近10轮对话原文（约40K tokens），更早的对话压缩为摘要（约4K tokens）。压缩使用LLM summarize，耗时约2s。实测：在128K上下文窗口下，此策略允许约50轮对话才触发压缩，对应约1小时的编码会话。替代方案（滑动窗口丢弃最早轮次）：会丢失早期设计决策上下文，导致代码不一致——本agent需要记住第3轮的需求来验证第48轮的代码。"
```

### 2. 架构选型无对比（权重25%）

```
❌ AI模式：
"采用while(true)循环作为agent主循环"
"使用tool approval flow保证安全性"
"通过repo map实现代码感知"

✅ 专业写法：
"agent主循环选用while(true)+tool_call而非ReAct框架——理由：(1) ReAct需要每步生成thought+action+observation，单步token消耗约200，而tool_call只需函数名+参数约50 tokens——以50轮对话计，ReAct多消耗7500 tokens/会话；(2) ReAct的推理链对编码任务价值低——代码修改是确定性的tool调用，不需要'思考'下一步。代价：while(true)需要外部doom loop检测器防止无限循环（3轮无tool调用则退出）。"
```

### 3. 性能指标缺失（权重20%）

```
❌ AI模式：
"上下文压缩效率高"
"工具调用响应快"
"内存占用低"

✅ 专业写法：
"上下文压缩：40K tokens原文→4K tokens摘要，压缩率10:1，LLM summarize耗时1.8s±0.3s（Claude 3.5 Sonnet，2025.3测试）。工具调用响应：本地工具（bash/grep）p50=120ms，API工具（GitHub）p50=2.3s。内存占用：单会话峰值约180MB（含LLM响应缓存），100并发会话约18GB——需要内存池回收机制（空闲>5分钟的会话释放缓存）。"
```

### 4. 安全规则泛泛（权重15%）

```
❌ AI模式：
"采用多层安全机制确保工具调用安全"
"对危险操作进行审批和限制"
"实现沙箱隔离执行"

✅ 专业写法：
"工具安全规则（3层）：
1. 语法层：禁止rm -rf /、git push --force等危险命令模式（正则匹配12条规则）
2. 审批层：git commit/push需要用户确认（Y/N），确认后60s内有效不复问
3. 沙箱层：bash命令在Docker容器中执行，容器无网络访问（--network=none），只读挂载项目目录（-v /repo:/repo:ro）

绕过记录：任何被语法层拦截的命令会记录到.trusted-dotfiles/bash-denied.log，含时间戳、命令原文、命中规则编号。"
```

### 5. 会话持久化无方案对比（权重15%）

```
❌ AI模式：
"使用SQLite持久化会话数据"
"支持JSONL格式的会话日志"

✅ 专业写法：
"会话持久化选用SQLite而非JSONL——理由：(1) JSONL每次读取需全量扫描，100轮对话=2MB扫描耗时50ms，SQLite的SELECT WHERE session_id=?耗时<1ms；(2) SQLite支持并发写入（WAL模式），JSONL需要文件锁；(3) SQLite的BLOB列可以存储压缩后的tool_output。代价：引入sqlite3依赖（Python标准库，无额外安装），数据库文件增长约每天500KB（100轮对话），需要VACUUM清理策略。"
```

## 代码架构文档反AIGC五原则

### 1. 每个模式选择标注排除理由

不写"采用X模式"，写"选X而非Y，因为Y在本agent场景下有[具体问题]"。

### 2. 所有性能描述配数字

不写"效率高"，写"压缩率10:1，耗时1.8s±0.3s"。

### 3. 安全规则写具体而非口号

不写"多层安全机制"，写"语法层12条正则+审批层Y/N+沙箱层Docker --network=none"。

### 4. 技术选型写约束而非通用优点

不写"SQLite稳定可靠"，写"SQLite的SELECT WHERE耗时<1ms vs JSONL全量扫描50ms"。

### 5. 标注替代方案和折衷

不写确定语气，写"代价是X"、"替代方案Y的劣势是Z"。

## AIGC率检测清单

### 内容检测
- [ ] 每个模式/架构选择是否有排除理由？→无理由=AI
- [ ] 性能指标是否有具体数字（ms、MB、tokens）？→无数字=AI
- [ ] 安全规则是否有具体实现（正则条数、审批方式、沙箱参数）？→口号式=AI
- [ ] 持久化/存储选型是否有方案对比？→直接定论=AI
- [ ] 是否有替代方案和折衷说明？→全确定=AI

### 语言检测
- [ ] 是否出现"采用X模式"而无具体实现？→有=AI
- [ ] 是否出现"高效/安全/可靠"等空洞形容词？→有=AI
- [ ] 性能描述是否有基准测试数据？→无=AI
- [ ] 架构描述是否可映射到具体代码结构？→不可映射=AI

### AIGC率评分标准

- 0-15%：像架构设计文档，每个选择有数据支撑
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，像设计模式教科书
- 51-70%：需重写，空有术语没有取舍
- 71-100%：纯AI模板，正确但无用
