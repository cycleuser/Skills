# 迭代管理报告反AIGC检测规则

迭代管理产生的文档（迭代进度报告、测试结果摘要、改进建议）面临独特的AIGC风险——迭代报告的核心是量化对比，容易被写成"有所改善"这类定性描述。好的迭代报告读起来像CI看板——红绿分明、数字说话、趋势可见；AI生成的读起来像周报，全是形容词没有数据。

## 核心原则

迭代管理报告反AIGC的关键是**度量有基线**和**趋势可追溯**。AI倾向生成"测试覆盖率有所提升"这种无基线的定性描述。人类写迭代报告会写"覆盖率68%→74%（+6%）"，会写哪个测试文件贡献了多少，会标注哪些指标在恶化。

## 迭代管理报告AIGC高发模式

### 1. 度量数据空洞（权重25%）

```
❌ AI模式：
"测试覆盖率有所提升"
"代码质量有所改善"
"本轮迭代整体进展良好"

问题：没有基线、没有具体数字、没有来源。

✅ 专业写法：
"测试覆盖率：68%→74%（+6%），主要贡献来源：
- test_auth.py：+4.2%（新增12个用例，覆盖3个边界条件）
- test_parser.py：+1.8%（新增5个用例，覆盖异常输入）

代码质量：ruff errors 23→8（-65%），剩余8个是E501 line-length问题（已在.gitignore标记忽略）。 pylint score：7.2→8.5（+1.3），提升来自移除未使用导入(5个)和添加类型注解(8个)。

性能指标：API p50延迟 120ms→45ms（-62.5%），根因：缓存层引入（Redis缓存命中率92%后）。并发测试：500连接无crash（前一轮200连接crash率15%）。"
```

### 2. 迭代进展只有定性描述（权重20%）

```
❌ AI模式：
"本轮迭代取得了显著成果"
"各项指标稳步提升"
"核心功能已基本完善"

✅ 专业写法：
"迭代#3进展报告：
| 指标 | 迭代#2 | 迭代#3 | 变化 | 目标 | 达标？ |
|------|--------|--------|------|------|--------|
| 测试覆盖率 | 68% | 74% | +6% | 80% | ❌（差6%） |
| ruff errors | 23 | 8 | -65% | 0 | ❌（差8个） |
| API延迟p50 | 120ms | 45ms | -62.5% | <50ms | ✅ |
| 已知bug | 5 | 1 | -80% | 0 | ❌（差1个） |
| GUI启动时间 | - | 2.8s | - | <2s | ❌（差40%） |

达标率：1/5（20%）。下轮迭代重点：测试覆盖率（需+6%）、ruff errors（需清零）、GUI启动时间（需缩短40%）。"
```

### 3. 测试结果只有通过/失败（权重20%）

```
❌ AI模式：
"所有测试均已通过"
"测试结果整体良好"
"发现了一些失败的测试"

✅ 专业写法：
"测试结果摘要：
总数：47个（通过45个，失败2个）
失败用例：
1. test_aggregate.py::test_large_input — OOM killed（退出码137），根因：pandas.read_csv对500MB文件全量加载。修复方案：分块读取（已实现在PR #23）
2. test_api.py::test_concurrent_login — 竞态条件（assertion error，2/10次复现）。根因：login()未加锁，并发5+请求时token碰撞。修复方案：加asyncio.Lock（需0.5天）

新增测试：12个（test_auth.py: 8个，test_parser.py: 4个）
删除测试：0个
跳过测试：3个（标记@pytest.mark.skip(reason='需要Redis环境')）

回归测试：0个回归（上一轮的全部45个通过用例本轮仍然通过）"
```

### 4. 改进建议不具体（权重15%）

```
❌ AI模式：
"建议进一步提升测试覆盖率"
"需要优化性能瓶颈"
"应该加强代码审查"

✅ 专业写法：
"改进建议（按影响排序）：
1. [高影响-30分钟] 修复test_aggregate.py::test_large_input → 分块读取（见PR #23）→ 预计覆盖率+1.2%
2. [高影响-0.5天] 给login()加asyncio.Lock → 消除test_concurrent_login竞态 → 预计稳定性+20%
3. [中影响-1天] 将8个E501 line-length errors修复 → ruff errors清零 → 达标
4. [中影响-2天] GUI启动优化（目标2.8s→2.0s）→ 方案：延迟加载QtWebEngine → 预计达标

不建议做的事：重写aggregate模块（影响面太大，当前仅需修复1个OOM用例）。"
```

### 5. 趋势分析无预测（权重10%）

```
❌ AI模式：
"整体趋势向好"
"如果保持当前速度，预计可以按时完成"

✅ 专业写法：
"趋势分析（5轮迭代数据）：
覆盖率趋势：62%→64%→66%→68%→74%（线性增长，+2.4%/轮），如维持增速→8轮达到82%（目标80%✅）
ruff errors趋势：34→28→23→23→8（非线性，本轮大幅下降），预计2轮内清零✅
性能趋势：延迟180ms→150ms→130ms→120ms→45ms（缓存引入后跳跃式改善）

风险预测：
- 覆盖率增长可能饱和（低垂果实已摘完，+2.4%/轮→+1.5%/轮预计从第6轮开始）
- GUI启动时间2.8s→2.0s需要架构级改动（延迟加载），1轮内完成概率30%
- 整体达标概率：3轮内80%（保守估计）"
```

### 6. 迭代间问题无追踪（权重10%）

```
❌ AI模式：
"之前发现的问题已经得到解决"
"遗留问题持续关注中"

✅ 专业写法：
"问题追踪（跨迭代）：
| ID | 描述 | 提出轮次 | 当前状态 | 变化 |
|----|------|---------|---------|------|
| #1 | API延迟>100ms | 迭代#1 | ✅已解决 | 120ms→45ms |
| #2 | Redis不可用 | 迭代#2 | ⬇️降级 | 改为内存队列 |
| #3 | GUI启动>2s | 迭代#2 | ❌未解决 | 2.8s（前值2.8s，无变化） |
| #5 | 并发>500内存泄漏 | 迭代#3 | ❌未解决 | 新提出，50MB/h |
| #4 | test_large_input OOM | 迭代#3 | 🔧修复中 | PR #23 |

问题解决率：1/5（20%），降级率：1/5（20%），新增问题：2个/轮。趋势：问题积压在增加。"
```

## 迭代管理报告反AIGC六原则

### 1. 度量数据有基线和来源

不写"覆盖率提升"，写"68%→74%（+6%），来源：test_auth.py新增12用例"。

### 2. 进展用数据表格呈现

不写"进展良好"，写"达标率1/5（20%），具体指标表格"。

### 3. 测试结果列出失败详情

不写"全部通过"，写"通过45个，失败2个（列出根因和修复方案）"。

### 4. 改进建议按影响排序配时间

不写"建议提升覆盖率"，写"[高影响-30min] 修复X → 覆盖率+1.2%"。

### 5. 趋势分析有预测和概率

不写"趋势向好"，写"如维持+2.4%/轮→8轮达82%（目标80%✅）"。

### 6. 问题跨迭代追踪

不写"问题已解决"，写"问题追踪表：ID/描述/状态/轮次/变化"。

## AIGC率检测清单

### 内容检测
- [ ] 度量数据是否有前后对比和基线？→无基线=AI
- [ ] 进展是否有达标/未达标分类？→全是达标=AI
- [ ] 测试结果是否有失败用例的具体根因？→只有通过/失败数=AI
- [ ] 改进建议是否有优先级、时间估计、预期影响？→笼统建议=AI
- [ ] 趋势分析是否有预测值和达标概率？→只有过去数据=AI
- [ ] 是否有问题追踪表？→无=AI

### 语言检测
- [ ] 是否出现"显著/稳步/良好/有所"等空洞修饰词？→大量出现=AI
- [ ] 数字是否有变化量（+6%、-65%）？→只有单点数=AI
- [ ] 是否有"不建议做的事"？→全是待改进=AI
- [ ] 是否有回归测试确认？→无=AI

### AIGC率评分标准

- 0-15%：像CI看板，红绿分明、数据说话、趋势可见
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，像周报全是形容词
- 51-70%：需重写，定性描述无量化支撑
- 71-100%：纯AI模板，万能形容词堆砌
