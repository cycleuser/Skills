# 技术文档反AIGC检测规则

技术文档（架构设计、项目规划、代码规范）面临的AIGC检测不同于文学或公务——它要求专业性，但不能是空洞的专业术语堆砌。好的技术文档读起来像资深架构师在白板前边画边讲，AI生成的读起来像模板填空。

## 核心原则

技术文档反AIGC的关键是**具体**和**有决策理由**。AI倾向生成正确的但可以放在任何项目里的泛泛之谈。人类工程师写技术文档会写"为什么选A不选B"，会写具体的数字和约束，会明确标注不确定的地方。

## 技术文档AIGC高发模式

### 1. 技术选型无理由（权重30%）

```
❌ AI模式：
"使用Python作为后端语言，因其丰富的生态系统"
"采用Flask框架，因其轻量灵活"
"选择PostgreSQL，因其稳定可靠"

问题：这些理由放在任何项目上都成立，毫无针对性。

✅ 专业写法：
"后端选用Python 3.10+，核心考量是数据处理的numpy/pandas生态——本项目需处理百万级CSV的实时聚合，C扩展的numpy比纯JS实现快40倍。Flask而非Django，是因为本系统只需5个REST端点，Django的ORM和模板引擎是多余的3MB依赖。PostgreSQL而非MySQL，因为本系统需要JSONB字段存储非结构化配置，且需要事务性的DDL，MySQL 8.0之前的版本不支持。"
```

### 2. 架构描述空洞（权重25%）

```
❌ AI模式：
"系统采用模块化设计，各模块职责明确，耦合度低"
"前端负责用户界面展示，后端负责业务逻辑处理，数据库负责数据存储"
"系统具有良好的可扩展性和可维护性"

✅ 专业写法：
"系统拆分为4个模块：core（数据聚合引擎，200行）、api（REST接口，100行）、cli（命令行入口，80行）、gui（PySide6界面，150行）。core无外部依赖，api依赖core，cli和gui都依赖api——这样单文件运行时只需core+cli，不强制安装PySide6（120MB）。"
```

### 3. 规格参数模糊（权重20%）

```
❌ AI模式：
"系统性能优异"
"响应速度快"
"支持高并发"
"具有良好的用户体验"

✅ 专业写法：
"API端点p50延迟<50ms（本地测试，万条记录聚合），p99<200ms"
"单实例支持200并发连接，超出需要水平扩展至2+实例"
"GUI启动时间<2s（冷启动），界面切换<100ms"
```

### 4. "首先其次最后"式设计文档（权重15%）

```
❌ AI模式：
"首先，系统需要实现数据采集功能。其次，需要实现数据处理功能。再次，需要实现数据存储功能。最后，需要实现数据展示功能。"

✅ 专业写法：
"数据流从采集到展示形成单向依赖链：采集模块产出RawData → 处理模块消费RawData产出AggData → 存储模块持久化AggData → 展示模块读AggData渲染视图。打破循环依赖的关键是：展示层不直接访问原始数据源，只能通过api模块获取处理后的数据。"
```

### 5. 不标注不确定性和折衷（权重10%）

```
❌ AI模式：
全文语气确定，所有设计决策都像唯一正确答案。

✅ 专业写法：
"缓存策略选LRU而非LFU，因为本系统访问模式偏向最近热点（p90数据集中在最近1小时）。如果后续用户行为变为长尾分布，需要切换为LFU，但这需要额外2天开发。——这里选LRU是折衷，不是唯一解。"

"以下两个方案均可，A方案开发快（3天）但查询慢（200ms），B方案开发慢（7天）但查询快（20ms）。本版先选A方案上线，v2切到B方案。"
```

## 技术文档反AIGC五原则

### 1. 每个技术决策标注理由

不写"选用X"，写"选用X因为[具体理由]，排除Y因为[具体理由]"。

### 2. 每个性能指标标注数字

不写"性能好"，写"p50 < 50ms, p99 < 200ms"。

### 3. 每个架构选择标注约束

不写"模块化设计"，写"core模块无外部依赖是因为[具体约束]"。

### 4. 不确定的地方明确标注

不写确定语气，写"此处有折衷"、"此处需后续验证"。

### 5. 打破机械递进

不用"首先其次最后"，用数据流关系、依赖关系、时间顺序等自然逻辑连接。

## AIGC率检测清单

### 内容检测
- [ ] 每个技术选择是否标注了排除理由？→无理由=AI
- [ ] 是否有具体性能数字？→无数字=AI
- [ ] 是否标注了不确定或折衷之处？→全确定=AI
- [ ] 架构描述是否可映射到具体代码结构？→不可映射=AI

### 语言检测
- [ ] 是否出现"首先其次最后"机械递进？→有=AI
- [ ] 是否出现"优异/良好/强大"等空洞形容词？→有=AI
- [ ] 技术选型理由是否适用于任何项目？→适用=AI
- [ ] 是否有量化指标而非定性描述？→定性=AI

### AIGC率评分标准

- 0-15%：像资深工程师写的设计文档
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，像模板填空
- 51-70%：需重写，空洞无实质
- 71-100%：纯AI模板
