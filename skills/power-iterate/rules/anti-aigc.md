# 迭代报告反AIGC检测规则

强力迭代产生的文档（迭代进度报告、决策日志、最终交付报告）面临独特的AIGC风险——它需要记录过程而非设计，容易用模糊的"进展顺利"替代具体数据。好的迭代报告读起来像工程师的现场笔记，有数字、有错误、有取舍；AI生成的读起来像项目汇报PPT，华而不实。

## 核心原则

迭代报告反AIGC的关键是**数据驱动**和**暴露问题**。AI倾向生成"一切正常"的平滑叙事，遗漏实际的错误、回退和折衷。人类写迭代报告会写具体数字（覆盖率从68%到74%），会记录失败路径（已尝试方案A但因X放弃），会标注不确定性（预算消耗比预估快30%）。

## 迭代报告AIGC高发模式

### 1. 进展描述模糊（权重30%）

```
❌ AI模式：
"本轮迭代取得了显著进展"
"核心功能已基本完成"
"测试覆盖率有所提升"
"性能优化效果明显"

问题：没有任何可量化的信息，可以套用于任何项目的任何迭代。

✅ 专业写法：
"迭代#3完成：覆盖率68%→74%（+6%），主要贡献来自test_auth.py新增的12个用例（覆盖3个边界条件：空用户名、过期token、并发登录）。core/aggregate.py的p50延迟从15ms升至23ms——这是性能回归，根因是pandas.groupby比dict comprehension慢10倍。标记：需在迭代#4替换为collections.Counter方案。"
```

### 2. 决策日志无理由（权重25%）

```
❌ AI模式：
"选择了JWT方案"
"决定使用Redis缓存"
"预算使用合理"

✅ 专业写法：
"决策ID:5 选择JWT而非Session——理由：(1)本系统是分布式API，Session需要Redis共享状态（增加1个依赖和0.5天配置）；(2)移动端无Cookie概念，JWT更适合；(3)JWT可携带角色信息减少数据库查询（从每次请求2次查询降为0次）。折衷：JWT无法主动失效，需配合黑名单机制（额外1天开发）。预算消耗：预估4天→实际5天（+25%），超出的1天花在JWT刷新token的竞态条件调试上。"
```

### 3. 最终报告泛泛结论（权重20%）

```
❌ AI模式：
"经过多轮迭代，系统达到预期目标"
"整体质量显著提升"
"用户体验得到改善"
"项目圆满完成"

✅ 专业写法：
"6轮迭代交付结果：测试覆盖率62%→89%（+27%），ruff errors 34→0（-100%），API p50延迟 120ms→45ms（-62.5%）。未达标项：GUI启动时间2.8s vs 目标2s（差40%），根因是PySide6加载QtWebEngine的3秒开销——v2计划用QML替代。已知缺陷：并发>500时内存泄漏（每小时增长50MB），需外部监控兜底。总耗时8天 vs 预算6天（+33%）。"
```

### 4. 错误和回退被隐藏（权重15%）

```
❌ AI模式：
"迭代过程中克服了技术困难"
"顺利解决了所有障碍"

✅ 专业写法：
"失败记录#2：尝试用aiohttp替换requests（预估提速3倍），实测仅提速12%——根因是本系统的瓶颈在数据库IO而非HTTP并发。回退到requests方案。浪费0.5天。教训：应先profile再优化。"
```

### 5. 度量指标无基线（权重10%）

```
❌ AI模式：
"代码质量显著改善"
"缺陷数量大幅减少"
"稳定性有所提升"

✅ 专业写法：
"代码质量：ruff errors 23→8（-65%），剩余8个是line-length问题（E501），已在.gitignore标记忽略。缺陷数：本轮新发现5个→修复4个→遗留1个（core/parser.py:67 的off-by-one，低优先级）。稳定性：连续运行24小时无crash（基线：迭代#2的12小时首次crash）。"
```

## 迭代报告反AIGC五原则

### 1. 每个进展标注具体数字

不写"覆盖率提升"，写"覆盖率68%→74%（+6%）"。

### 2. 每个决策标注排除理由

不写"选择X方案"，写"选择X而非Y，因为[理由]，Y的劣势是[具体问题]"。

### 3. 记录失败路径

不写"克服了困难"，写"尝试X方案失败，根因是[具体原因]，回退到Y方案，浪费N天"。

### 4. 标注预算偏差

不写"预算使用合理"，写"预估N天→实际M天（+X%），超出原因[具体]"。

### 5. 未达标项明确列出

不写"圆满完成"，写"达标项[A,B,C]，未达标项[D（差X%）]，遗留问题[E]"。

## AIGC率检测清单

### 内容检测
- [ ] 进展描述是否包含量化数据（覆盖率、错误数、延迟ms）？→无数据=AI
- [ ] 每个决策是否有排除理由？→无理由=AI
- [ ] 是否记录了失败的尝试和回退路径？→只写成功=AI
- [ ] 预算消耗是否有实际vs预估对比？→无对比=AI
- [ ] 是否有明确的未达标项和遗留问题？→全部达标=AI

### 语言检测
- [ ] 是否出现"显著/明显/大幅/圆满"等模糊修饰？→大量出现=AI
- [ ] 是否出现"克服困难/顺利解决"等套话？→有=AI
- [ ] 数字是否有基线对比（从X到Y）？→只有单点数字=AI
- [ ] 是否有具体错误信息（异常名、文件名、行号）？→无=AI

### AIGC率评分标准

- 0-15%：像工程师的迭代笔记，数据详实、问题透明
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，进展描述太模糊
- 51-70%：需重写，像项目汇报PPT而非技术文档
- 71-100%：纯AI模板，无实质内容
