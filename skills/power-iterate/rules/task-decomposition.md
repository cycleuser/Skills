# 自主任务分解规则

## 分解哲学

**原则**: 不询问、自主补全、边做边改

### 分解策略

| 情况 | 处理方式 |
|-----|---------|
| 需求明确 | 按需求分解 |
| 需求模糊 | 自行假设合理范围，标注`[假设]` |
| 需求缺失 | 采用最小可行方案，标注`[默认]` |
| 技术栈未指定 | 选择最主流技术，标注`[自主选择]` |

## 分解流程

```
[用户输入] → [提取关键信息] → [补充默认值] → [标注假设] → [生成任务队列]
```

### 步骤1：提取关键信息

从用户输入中提取：

```
## 关键信息提取

**目标**: [核心目标，1句话]
**类型**: [CLI工具/Web应用/库/脚本/...]
**技术栈**: [明确指定的或无]
**功能需求**: [列出的功能点]
**非功能需求**: [性能/安全/可扩展性/...]
**输出形式**: [可执行文件/API/库/文档/...]
**约束**: [明确指定的约束]
```

### 步骤2：补充默认值

| 缺失项 | 默认值 | 标注 |
|-------|-------|-----|
| 语言/框架 | 最主流选择 | `[假设:采用Python，因其生态完善]` |
| 架构 | 最简单可行 | `[假设:单文件架构，适合小型工具]` |
| 存储 | 无持久化 | `[假设:纯内存操作，无需数据库]` |
| 认证 | 无 | `[假设:暂不实现认证功能]` |
| 错误处理 | 基础处理 | `[假设:仅处理明显错误]` |
| 测试 | 基础验证 | `[假设:只做导入测试和基本功能测试]` |

### 步骤3：分解任务

**分解模板**:

```markdown
## 任务分解

### P0 - 最小可运行（必须在预算内完成）
| # | 任务 | 预计时间 | 验证方式 |
|---|-----|---------|---------|
| 0.1 | 项目结构创建 | 3min | 目录存在，可导入 |
| 0.2 | 核心功能实现 | 10min | 基本功能可执行 |
| 0.3 | 基本验证 | 5min | 无语法错误，可运行 |

### P1 - 完整功能（如有时间）
| # | 任务 | 预计时间 | 验证方式 |
|---|-----|---------|---------|
| 1.1 | 功能模块A | 10min | 功能测试通过 |
| 1.2 | 功能模块B | 10min | 功能测试通过 |
| 1.3 | 模块集成 | 5min | 集成测试通过 |

### P2 - 完善优化（尽量不做）
| # | 任务 | 预计时间 | 验证方式 |
|---|-----|---------|---------|
| 2.1 | 性能优化 | 15min | 性能指标达标 |
| 2.2 | 文档完善 | 10min | 文档可读 |
```

### 分解原则

1. **5-15分钟规则**: 每个任务5-15分钟
2. **可验证**: 每个任务完成后可验证
3. **独立化**: 尽量减少任务间依赖
4. **P0优先**: P0任务必须完成，P1尽量完成，P2尽量不做

### 时间分配建议

| 预算级别 | P0时间 | P1时间 | P2时间 |
|---------|-------|-------|-------|
| tiny (10min) | 7min | 3min | 0min |
| small (30min) | 15min | 12min | 3min |
| medium (60min) | 25min | 25min | 10min |
| large (120min) | 40min | 50min | 30min |
| xlarge (240min) | 60min | 100min | 80min |

## 任务队列管理

### 队列格式

```markdown
## 工作队列

### 待执行
1. [ ] 0.1 项目结构创建
2. [ ] 0.2 核心功能实现
3. [ ] 0.3 基本验证

### 执行中
- 1.1 功能模块A (进行中)

### 已完成
- [x] 0.1 项目结构创建

### 已跳过
- [s] 2.1 性能优化 (时间不足)
```

### 队列调整规则

1. **前置任务失败**: 跳过依赖任务，标记`[依赖失败]`
2. **时间不足**: 停止P2任务，标记`[时间不足]`
3. **任务拆分**: 如任务超过15分钟，自动拆分为子任务

## 自主决策规则

### 决策树

```
任务执行遇到选择时:

1. 有明确最佳实践?
   → 使用最佳实践

2. 有多种合理选择?
   → 选择最主流/最简单的

3. 无法决定?
   → 选择最安全的，记录`[待确认]`

4. 需要外部资源?
   → 先用mock/placeholder，后续替换
```

### 常见决策示例

| 情况 | 决策 | 记录 |
|-----|------|-----|
| 文件命名 | snake_case | - |
| 配置格式 | JSON/YAML | `[假设:JSON更通用]` |
| 日志级别 | INFO | - |
| 异常处理 | 基础处理+日志 | - |
| 依赖版本 | 最新稳定版 | `[假设:使用最新稳定版本]` |
| 代码风格 | PEP8/原生风格 | - |

## 假设管理

### 假设记录格式

```markdown
## 假设清单

| # | 假设内容 | 理由 | 影响 |
|---|---------|-----|-----|
| 1 | 使用Python 3.10+ | 生态完善 | 需要运行时支持 |
| 2 | 单文件架构 | 简单快速 | 不适合复杂逻辑 |
| 3 | CSV输入，JSON输出 | 用户未指定 | 可扩展 |
```

### 假设验证

- 假设在执行过程中被验证
- 错误的假设记录到`待修复清单`
- 不因此停止执行
