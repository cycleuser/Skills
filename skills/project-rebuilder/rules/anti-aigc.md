# 项目重建分析报告反AIGC检测规则

项目重建产生的文档（分析报告、特性评估、重建规划、重建进度报告）面临独特的AIGC风险——分析一个已有项目并规划重建，容易被写成正确的但无信息量的泛泛总结。好的分析报告读起来像你在code review一个项目，具体到文件行数和API端点；AI生成的读起来像课程作业的读后感，大词堆砌。

## 核心原则

项目重建分析反AIGC的关键是**代码级证据**和**量化对比**。AI倾向生成"该模块功能复杂"这类可以在任何项目上成立的描述。人类写分析报告会写具体的文件数、代码行数、依赖数、圈复杂度，会标注哪些特性可以1:1重建、哪些需要重新设计。

## 项目重建分析AIGC高发模式

### 1. 特性评估空泛（权重25%）

```
❌ AI模式：
"该特性实现较为复杂"
"此模块功能完备"
"核心功能稳定可靠"
"整体架构设计合理"

问题：这些评价可以套在任何一个项目上。

✅ 专业写法：
"特性A（数据聚合）：核心模块，实现复杂度8/10——涉及并发安全（需要RWLock，见core/aggregate.py:45-67）、事务回滚（需要2PC，见db/transaction.py:23）、和3个外部API调用（每个有独立的错误处理路径，见api/callers.py:89-156）。预估重建工时：4天。可1:1重建比例：70%（并发部分需要重新设计，因为原实现用threading而非asyncio）。"
```

### 2. 分析报告无代码证据（权重20%）

```
❌ AI模式：
"项目使用了多种设计模式"
"代码质量整体良好"
"存在一些技术债务"

✅ 专业写法：
"设计模式使用：Strategy模式3处（payment/strategy.py:12, notification/strategy.py:8, export/strategy.py:15），Observer模式1处（event/dispatcher.py:34）——策略模式过度使用，3处可合并为1个泛型Strategy[T]。代码质量：ruff扫描结果——errors: 23（其中E501 line-length: 15个，F841 unused variable: 8个），warnings: 47。技术债务：5处TODO标记（见grep -rn 'TODO' src/），2处硬编码配置（database URL in config.py:5，API key in settings.py:89——需要移到环境变量）。"
```

### 3. 重建规划无优先级（权重20%）

```
❌ AI模式：
"首先重建核心模块，然后重建辅助模块，最后进行集成测试"
"按照依赖关系逐步重建"

✅ 专业写法：
"重建优先级（按阻断关系排序）：
P0-必须先建（其他模块依赖它）：core模块（数据聚合引擎，0外部依赖，200行）——预计1天
P1-可以并行：api模块（依赖core，100行，5个REST端点）+ cli模块（依赖api，80行）——预计1天（并行）
P2-依赖P0+P1全部完成：gui模块（依赖api，需要PySide6，估计150行但调试量大）——预计2天
P3-收尾：集成测试（需要全部模块）+ 性能基准测试——预计1天

关键路径：P0→P2→P3 = 4天。并行路径：P0→P1(1天但需等待P0完成)→P3 = 4天。并行不缩短总工期（P2是瓶颈）。"
```

### 4. 项目对比无差异点（权重15%）

```
❌ AI模式：
"两个项目功能相似但实现不同"
"原项目使用技术栈A，新项目使用技术栈B"
"重建需要保留核心功能"

✅ 专业写法：
"原项目 vs 重建目标差异：
| 维度 | 原项目 | 重建目标 | 差异影响 |
|------|--------|---------|---------|
| 语言 | Python 2.7 | Python 3.10+ | 需重写所有f-string和类型注解 |
| 框架 | Django 1.11 | Flask 3.0 | ORM需替换为SQLAlchemy（+2天） |
| 并发 | threading | asyncio | 并发模型完全不同，core模块需重新设计 |
| 测试 | 无 | pytest 90%覆盖率 | 需从零写测试（+3天） |
| CI/CD | 无 | GitHub Actions | 需新建（+0.5天） |

不可1:1重建的部分：core/worker.py（580行，threading→asyncio需要完全重写），api/serializers.py（Django REST framework→Flask marshmallow需要完全重写）。"
```

### 5. 进度报告模糊（权重10%）

```
❌ AI模式：
"核心模块重建进展顺利"
"整体进度符合预期"
"主要功能已经完成"

✅ 专业写法：
"重建进度（第3天/共5天）：
- core模块：完成100%（200行，ruff errors 0，测试12/12 pass）
- api模块：完成80%（5个端点完成4个，缺失DELETE /items/:id，预计0.5天）
- cli模块：完成50%（3个命令完成2个，缺失export命令）
- gui模块：未开始（预计2天，是关键路径瓶颈）

进度风险：gui模块的PySide6依赖在CI环境安装耗时8分钟（Docker构建），需要预构建base image。"
```

### 6. 重建决策无取舍（权重10%）

```
❌ AI模式：
"对原有设计进行了优化改进"
"保留了核心功能，去除了冗余部分"

✅ 专业写法：
"重建决策3项：
1. 去除Django ORM→改用SQLAlchemy：原因是本项目只有5个模型，Django ORM的迁移框架是过度依赖（+2MB），但损失了Django Admin后台（需手动写管理界面，+1天）
2. 去除Celery→改用内存队列：原因是本项目并发<50，Celery需要Redis依赖（+1天配置），但损失了任务持久化（进程重启丢失，可接受——本系统是即时处理非批处理）
3. 保留原项目的CSV解析逻辑（core/parser.py:23-89）：原因是这段代码已处理过所有边界情况（3个TODO标记的bug已在v2.1修复），重写风险高于直接迁移"
```

## 项目重建分析反AIGC六原则

### 1. 特性评估量化和评级

不写"功能复杂"，写"复杂度8/10，涉及并发安全（具体文件:行号）"。

### 2. 分析报告引用代码证据

不写"代码质量良好"，写"ruff errors 23个（列出类型分布）"。

### 3. 重建规划标注关键路径

不写"逐步重建"，写"P0→P2→P3关键路径=4天，并行不缩短工期"。

### 4. 项目对比用表格列差异

不写"实现不同"，写"语言/框架/并发模型具体差异表"。

### 5. 进度报告百分比+具体完成项

不写"进展顺利"，写"api模块完成80%（4/5端点）"。

### 6. 重建决策写取舍

不写"优化改进"，写"去除X→改Y，损失Z（可接受因为W）"。

## AIGC率检测清单

### 内容检测
- [ ] 特性评估是否有复杂度评分和代码证据？→无=AI
- [ ] 分析报告是否引用了具体文件、行号、工具输出？→无=AI
- [ ] 重建规划是否有P0/P1/P2优先级和关键路径？→无=AI
- [ ] 项目对比是否有量化差异表？→无=AI
- [ ] 进度报告是否有百分比和具体完成项？→无=AI

### 语言检测
- [ ] 是否出现"合理/完善/稳定/顺利"等万能评价？→大量出现=AI
- [ ] 是否出现"首先然后最后"机械递进？→有=AI
- [ ] 数字是否有来源（工具输出、代码统计）？→无来源=AI
- [ ] 重建决策是否包含"损失/代价/折衷"？→全是收益=AI

### AIGC率评分标准

- 0-15%：像工程经理的项目分析，数据驱动、取舍透明
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，特征评估像读后感
- 51-70%：需重写，泛泛而谈无实质内容
- 71-100%：纯AI模板，可套用于任何项目
