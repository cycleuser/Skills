# 自治执行报告反AIGC检测规则

修仙（sleepless）产生的文档（交付报告、自愈日志、决策记录）面临独特的AIGC风险——自治执行强调"永不停止直到完成"，容易把所有过程写成平滑叙事。好的执行报告读起来像值班工程师的交接日志，有具体错误栈、有回退决策、有资源消耗数据；AI生成的读起来像顺利的项目总结，问题被抹平、错误被美化。

## 核心原则

自治执行报告反AIGC的关键是**暴露失败**和**量化资源**。AI倾向生成"自动修复了所有问题"的平滑叙事。人类写执行日志会写具体的异常名和行号，会写回退方案和浪费的时间，会标注哪些问题是降级解决而非真正修复的。

## 自治执行报告AIGC高发模式

### 1. 交付报告进展模糊（权重25%）

```
❌ AI模式：
"所有任务已顺利完成"
"系统自动修复了遇到的所有问题"
"最终交付质量达到预期"

✅ 专业写法：
"交付结果：4个任务完成，1个任务降级完成，0个任务未完成。
- 任务A（数据库迁移）：完成，迁移了23,456条记录，耗时12分钟
- 任务B（API重构）：完成，ruff errors 34→0
- 任务C（GUI开发）：降级完成——PySide6 WebEngine加载超时（3s>2s目标），改用QML方案交付（功能等价，外观有差异）
- 任务D（性能优化）：完成，p50延迟 120ms→45ms
- 任务E（并发测试）：未完成——并发>500时内存泄漏每小时50MB，需外部监控兜底，标记v2解决

总耗时6.2小时 vs 预算8小时（使用77.5%）"
```

### 2. 自愈日志无细节（权重25%）

```
❌ AI模式：
"遇到了错误并自动修复"
"自动切换了方案"
"系统自动恢复了"

✅ 专业写法：
"自愈#3: Redis连接超时（ConnectionRefusedError: [Errno 61] Connection refused），根因分析：本地未安装Redis Server（端口6379无响应）。修复方案：从redis-queue改为内存queue.Queue。降级影响：进程重启后队列数据丢失——可接受，因为队列是临时任务列表非持久数据。标记[降级]。耗时：诊断2分钟+修复3分钟=5分钟。"

"自愈#7: 测试test_aggregate.py::test_large_input OOM killed（退出码137），根因：pandas.read_csv对500MB文件全量加载。修复方案：分块读取（chunksize=50000）。无降级影响。耗时：诊断1分钟+修复4分钟=5分钟。"
```

### 3. 决策记录无理由（权重20%）

```
❌ AI模式：
"选择了更优的方案"
"根据实际情况调整了策略"
"优化了实现路径"

✅ 专业写法：
"决策#4: 放弃方案A（Celery任务队列），改用方案B（内存队列+多线程）——理由：(1)Celery需要Redis/RabbitMQ依赖，当前环境未安装（自愈#3已降级为内存队列，回退增加复杂度）；(2)本系统并发量<50（从日志统计），Celery的分布式优势在此规模下无意义；(3)实现时间：Celery方案3天 vs 内存队列0.5天。折衷：进程重启时任务丢失，但已通过graceful shutdown hook保证重启前持久化到磁盘。标记[自决]——用户未指定，基于当前环境约束决策。"
```

### 4. 资源消耗无基线（权重15%）

```
❌ AI模式：
"预算使用合理"
"资源消耗在可控范围内"
"整体效率较高"

✅ 专业写法：
"资源消耗统计：
- Token使用：487K tokens / 800K预算（60.9%）
- 时间消耗：6.2小时 / 8小时预算（77.5%）
- 自愈次数：7次（其中3次降级解决、4次完全修复）
- 测试运行：23次（总耗时47分钟，平均2分3秒/次）
- 回退次数：2次（方案A→B 和 方案C→D）

效率指标：有效工作时间5.1小时 / 总时间6.2小时 = 82.3%（其余17.7%用于自愈和回退）"
```

### 5. 问题记录被抹平（权重15%）

```
❌ AI模式：
"过程中遇到一些小问题，均已解决"
"系统展现了良好的自愈能力"

✅ 专业写法：
"未解决问题（1项）：并发>500时内存泄漏——每小时增长50MB（从/proc/PID/smaps测得），根因未定位（疑似aiohttp ConnectorPool未释放）。临时措施：每6小时crontab重启Worker进程。标记：需v2定位根因。

降级解决（3项）：
1. Redis不可用 → 改为内存队列（数据不持久化）
2. PySide6 WebEngine超时 → 改为QML（外观差异5%）
3. Celery不可用 → 改为多线程（并发上限50）"
```

## 自治执行报告反AIGC五原则

### 1. 交付报告列出完成/降级/未完成

不写"全部完成"，写"4完成、1降级、0未完成"。

### 2. 自愈日志写具体异常和处理方案

不写"自动修复了错误"，写"ConnectionRefusedError→降级为内存队列，数据不持久化"。

### 3. 决策记录写排除理由和环境约束

不写"选择了更优方案"，写"选B而非A，因为[约束]，A的劣势[具体]"。

### 4. 资源消耗量化且对比基线

不写"预算使用合理"，写"Token 487K/800K（60.9%），时间6.2h/8h（77.5%）"。

### 5. 问题如实记录不抹平

不写"均已解决"，写"X项降级解决（列出）、Y项未解决（列出）"。

## AIGC率检测清单

### 内容检测
- [ ] 交付报告是否有完成/降级/未完成的分类统计？→全是完成=AI
- [ ] 自愈日志是否包含具体异常名和行号？→只有"遇到错误"=AI
- [ ] 每个决策是否标注了排除理由？→无理由=AI
- [ ] 资源消耗是否量化（token数、时间h）？→无数字=AI
- [ ] 是否有明确的未解决问题？→无任何遗留=AI

### 语言检测
- [ ] 是否出现"全部完成/均已解决/圆满"等报喜不报忧用语？→大量出现=AI
- [ ] 是否有具体的异常名（如ConnectionRefusedError）？→无=AI
- [ ] 是否出现降级[降级]标记？→无=AI
- [ ] 决策是否标注了[自决]标记（用户未指定）？→无=AI

### AIGC率评分标准

- 0-15%：像值班工程师的交接日志，数据详实、问题透明
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，问题被模糊化处理
- 51-70%：需重写，像顺利的项目总结而非真实执行报告
- 71-100%：纯AI模板，报喜不报忧
