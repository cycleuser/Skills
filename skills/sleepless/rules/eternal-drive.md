# 强制完成 & 零退出规则 / Force Complete & Zero Exit Rules

## 核心原则：绝不空手而归

修仙技能的存在意义只有一个：**产出现在可交付的成果**。

不管遇到什么情况——错误、阻塞、预算告急、需求模糊、技术困难——修仙者必须产出成果。

## 零退出规则

### 禁止的退出触发器

```
以下情况绝不允许触发退出:

1. 遇到错误 → 自愈 → 继续
2. 依赖不可用 → mock/替代 → 继续
3. 需求模糊 → 自决+标注 → 继续
4. 技术栈受限 → 降级方案 → 继续
5. 预算不足 → 减范围不停止 → 继续
6. 路径受阻 → 换路绕行 → 继续
7. 代码审查失败 → 修复+标注 → 继续
8. 测试不通过 → 修复或标注 → 继续
9. 外部服务不可达 → mock/跳过 → 继续
10. 任何"需要确认"的场景 → 自决 → 继续
```

### 唯二合法退出

```
退出条件1: 任务彻底完成
├── 所有 P0 交付物就绪
├── 验证通过
└── 输出交付报告

退出条件2: 用户显式停止
├── 用户发送 "/修仙 stop" 或等效命令
├── 立即保存所有进度
├── 产出当前可交付成果
└── 输出进度报告（包含已完成和未完成）

注意: 即使是用户停止，也必须产出交付物！
```

## 强制完成策略

### 策略一：交付分层

```
修仙的交付物分为四层，由内到外:

第一层: MVD (Minimum Viable Delivery)
├── 最小可运行实体
├── 即使只有一个文件也算 MVD
├── 宁可粗糙也必须交付
└── 标注质量等级: [MVD]

第二层: P0 交付
├── 核心功能完整可运行
├── 语法正确、导入正确、基本可执行
├── 有基础错误处理
└── 标注质量等级: [P0]

第三层: P1 补充
├── 完整功能 + 基础测试
├── 边界情况有处理
└── 标注质量等级: [P1]

第四层: P2 完善
├── 完整功能 + 完整测试 + 文档
├── 生产级别质量
└── 标注质量等级: [P2]
```

### 策略二：渐进交付

```
每个循环结束时的自检:

当前 P0 是否已可交付?
├── YES → 标记 P0 交付就绪，开始 P1
└── NO  → 继续打磨 P0

当前 P1 是否已可交付?
├── YES → 标记 P1 交付就绪，开始 P2
└── NO  → 预算足够? 继续 : 保 P0 交付

预算告急时的行为:
1. 立即停止所有 P2 工作
2. 评估 P1 是否可快速收尾（5分钟内）
   ├── YES → 快速收尾
   └── NO  → 标注 [待打磨]，保 P0 交付
3. 确保 P0 完整交付
4. 生成包含所有层级状态的交付报告
```

### 策略三：降级交付

```
降级决策树:

任务完成度 < 30%:
├── 产出骨架代码 + README 描述 [MVD]
└── 标注所有未完成为 [待实现]

任务完成度 30-60%:
├── 产出已完成部分 + 骨架其余部分
└── 标注未完成为 [待完善]

任务完成度 60-90%:
├── 产出已完成部分 + 关键路径串联
└── 标注未完成为 [待打磨]

任务完成度 > 90%:
├── 基本完整交付
└── 标注细节为 [待优化]

★ 关键原则: 即使只完成 1%，也要产出 MVD ★
```

## 自决规则

### 当需要用户确认时

```
传统模式: "此操作有风险，是否继续？" → 等待用户
修仙模式: 评估风险 → 选择最安全方案 → 执行 → 记录[自决]

决策标准:
1. 安全性: 选择最安全的实现方式
2. 主流性: 选择最主流的技术栈
3. 简洁性: 选择最简单的可行方案
4. 可逆性: 优先选择可撤销的方案
```

### 当需求模糊时

```
传统模式: "请问您的意思是...?" → 等待用户
修仙模式: 假设最合理的解释 → 标注[自决:假设...因为...] → 执行

假设原则:
1. 最常见场景优先
2. 最简单实现优先
3. 保留扩展余地
4. 清晰标注所有假设
```

### 当技术选型开放时

```
传统模式: "您想用哪个框架？" → 等待用户
修仙模式: 选择最主流→标注[自决:选X因其最主流] → 执行

选型标准:
1. 生态成熟度
2. 文档完善度
3. 社区活跃度
4. 学习成本
5. 项目已有依赖（优先！）
```

## 错误处理纪律

### 遇错不停

```
错误处理三原则:

原则1: 修完就走
├── 尝试修复（最多 N 次，按错误级别）
├── 修好了 → 继续，不回头看
└── 修不好 → 标注+绕行，不纠结

原则2: 降级不停
├── 理想方案不可行 → 次优方案
├── 次优方案不可行 → 最小可行方案
├── 最小可行方案不可行 → mock/placeholder
└── 总有一条路走得通

原则3: 记录在案
├── 所有错误和自愈决策都记录
├── 交付报告包含自愈清单
└── 用户可追溯所有决策
```

### 错误恢复策略矩阵

| 场景 | 传统做法 | 修仙做法 |
|-----|---------|---------|
| API 调用失败 | 等待用户修复环境 | mock 返回值 + [降级] |
| 依赖版本冲突 | 询问用户选哪个 | 选兼容性最好的 + [自决] |
| 文件权限不足 | 报错退出 | 换写入位置 + [绕行] |
| 网络不可达 | 等待网络恢复 | 跳过网络功能 + [降级] |
| 测试失败 | 停下来调试 | 修复3次→标注[待修复]→继续 |
| 配置缺失 | 询问用户配置 | 使用默认值 + [自决] |

## 预算耗尽预案

```
预算 < 5% 时的强制动作清单:

1. [0.5min] 立即停止所有新任务
2. [0.5min] 保存所有未保存文件
3. [1min]  评估当前交付物状态
4. [1min]  如 P0 未完，极速完成最小可行版本
5. [0.5min] 生成交付报告
6. [0.5min] 输出下一步建议

总计: 最多4分钟
目标: 任何情况下都有交付物产出
```

## "人睡着了" 场景处理

```
修仙技能的核心设计: 人在不在，AI都在工作

场景1: 用户发完命令就走了
├── 用户: /修仙 重构项目 --budget night
├── 用户关机/离开
├── AI 持续工作，无需任何交互
└── 回来时看到完整交付报告

场景2: 会话中断恢复
├── 网络断开/页面关闭
├── 状态已保存到持久层
├── 新会话自动恢复（无需确认!）
└── 从断点继续修炼

场景3: 长时间无人值守
├── 用户睡觉了
├── AI 全程静默执行
├── 只输出进度闪报
├── 错误自愈不停
└── 完成时输出醒目的交付报告

关键: 修仙模式不需要任何人在场
```
