# 全任务模式规则 / All Task Modes Rules

## 模式总览

修仙技能支持八种任务模式，每种模式有独立的循环策略、验证标准和降级方案。

## 模式1：开发 (Dev)

### 适用场景
- 新功能开发、新项目构建、全栈实现

### 循环策略
```
1. 骨架优先: 项目结构 → 核心模块 → 辅助模块
2. 功能逐项: P0功能逐个实现，每个实现后即验证
3. 连通优先: 确保端到端通路优先于单模块完美
4. 快速集成: 模块间尽早集成，避免后期大集成
```

### 验证标准
```
P0验证:
- 语法正确 (python -m py_compile / tsc / 等)
- 导入正确 (模块可导入)
- 核心路径可运行 (主功能通路)
- 基本错误处理 (无效输入不crash)

P1验证:
- P0全部通过
- 边界情况有处理
- 配置可调
- 日志输出合理

P2验证:
- P1全部通过
- 测试覆盖 > 70%
- 类型注解完整
- 文档完整
```

### 降级方案
```
理想: 完整功能实现
降级1: 核心功能实现 + 标注[待完善]
降级2: 最小可用版本 + 标注[MVD]
降级3: 骨架代码 + README + 标注[待实现]
```

### 交付物定义
```
P0: 可运行的核心功能代码
P1: + 边界处理 + 基础测试
P2: + 完整测试 + 类型注解 + 文档
```

## 模式2：修复 (Fix)

### 适用场景
- Bug 修复、问题排查、热修复

### 循环策略
```
1. 复现优先: 先复现问题，确认Bug存在
2. 根因驱动: 找根因，而非表面修复
3. 逐个消灭: 一个Bug一个循环，不复盘
4. 回归保护: 修复后确认不引入新问题
```

### 验证标准
```
P0验证:
- Bug 症状消失
- 原有功能仍然工作
- 错误日志清零（针对该Bug）

P1验证:
- P0全部通过
- 添加了回归测试
- 相关边界情况验证

P2验证:
- P1全部通过
- 根因分析报告
- 防御性代码（防止同类Bug）
```

### 降级方案
```
理想: 根因修复 + 回归测试
降级1: 根因修复 + 标注[待补测试]
降级2: 姑息修复（如try/catch包住）+ [临时修复]
降级3: 标注规避方案 + [规避建议]
```

### 交付物定义
```
P0: Bug 修复代码
P1: + 回归测试
P2: + 根因报告 + 防御代码
```

## 模式3：重构 (Refactor)

### 适用场景
- 代码重构、架构调整、性能优化

### 循环策略
```
1. 行为保持: 重构不改变外部行为
2. 小步快跑: 每次只重构一个模块/文件
3. 持续验证: 每次重构后运行测试
4. 渐进改善: 不追求一步到位
```

### 验证标准
```
P0验证:
- 重构前后行为一致
- 所有已有测试仍然通过
- 代码结构有改善

P1验证:
- P0全部通过
- 新增了结构改善的测试
- 命名更清晰
- 依赖更合理

P2验证:
- P1全部通过
- 性能指标改善
- 文档更新
```

### 降级方案
```
理想: 完整重构 + 测试 + 文档
降级1: 核心模块重构完成 + 标注[待重构]
降级2: 最关键模块重构 + 其余标注[待重构]
降级3: 重构计划文档 + 已重构部分交付
```

### 交付物定义
```
P0: 重构代码（行为不变）
P1: + 结构改善测试
P2: + 性能验证 + 文档
```

## 模式4：测试 (Test)

### 适用场景
- 测试编写、覆盖率提升、质量保障

### 循环策略
```
1. 核心先行: 先给最核心的功能写测试
2. 覆盖逐块: 按模块逐块提升覆盖率
3. 失效驱动: 发现Bug时优先写测试再修复
4. 梯度提升: 烟雾→单元→集成→端到端
```

### 验证标准
```
P0验证:
- 测试可运行
- 核心模块有基本测试
- 测试通过率 > 80%

P1验证:
- 覆盖率 > 60%
- 边界情况有测试
- 通过率 100%

P2验证:
- 覆盖率 > 80%
- 完整测试套件
- CI 可集成
```

### 降级方案
```
理想: 完整测试套件
降级1: 核心模块测试完整 + 标注[待补测试]
降级2: 烟雾测试通过 + 标注[MVD测试]
降级3: 测试计划 + 最少测试用例
```

### 交付物定义
```
P0: 可运行的测试文件
P1: + 边界测试 + 覆盖率提升
P2: + 完整套件 + CI 集成
```

## 模式5：文档 (Doc)

### 适用场景
- 文档编写、README、API 文档

### 循环策略
```
1. 核心章节先行: Overview → Quick Start → API
2. 示例驱动: 每个功能点配一个示例
3. 双语并行: 中英文同步编写
4. 审阅循环: 写完→自审→修正
```

### 验证标准
```
P0验证:
- README 存在且可读
- 安装步骤可执行
- 基本API有文档

P1验证:
- 所有公开API有文档
- 示例代码可运行
- 中英文齐全

P2验证:
- 架构文档完整
- FAQ 存在
- 贡献指南存在
```

### 降级方案
```
理想: 完整文档套件
降级1: 核心文档完整 + 标注[待补充]
降级2: README + API概要 + 标注[MVD文档]
降级3: README骨架 + 标注[待编写]
```

### 交付物定义
```
P0: README + 基本API文档
P1: + 完整API文档 + 示例
P2: + 架构文档 + FAQ + 贡献指南
```

## 模式6：迭代 (Iterate)

### 适用场景
- 持续改进、多轮打磨、质量提升

### 循环策略
```
1. 度量先行: 每轮开始前记录当前指标
2. 定向改进: 每轮只改进一个维度
3. 验证收敛: 每轮改进后验证指标提升
4. 及时止损: 连续2轮无改善则换方向
```

### 验证标准
```
P0验证:
- 至少完成了1轮完整改进
- 指标有可量化改善

P1验证:
- 完成了N轮改进（N由预算决定）
- 多维度指标提升

P2验证:
- 目标指标全部达标
- 改进报告详细
```

### 降级方案
```
理想: 目标指标全部达标
降级1: 核心指标达标 + 次要指标标注[待打磨]
降级2: 部分指标改善 + 改进报告
降级3: 诊断报告 + 改进计划
```

### 交付物定义
```
P0: 改进后的代码/文档
P1: + 改进对比报告
P2: + 目标达成报告
```

## 模式7：集成 (Integrate)

### 适用场景
- 多技能协同、跨模块整合、系统集成

### 循环策略
```
1. 接口先行: 先定义/确认接口契约
2. 逐项对接: 按接口逐项实现对接
3. 数据流验证: 每对接一个接口即验证数据流
4. 端到端贯通: 优先全链路跑通
```

### 验证标准
```
P0验证:
- 核心接口可通信
- 数据可流转
- 基本端到端跑通

P1验证:
- 全部接口对接完成
- 错误场景有处理
- 状态一致性验证

P2验证:
- 性能测试通过
- 完整集成测试
- 监控/日志完整
```

### 降级方案
```
理想: 完整集成
降级1: 核心链路跑通 + 标注[待集成]
降级2: mock接口跑通 + 标注[待替换]
降级3: 集成方案文档 + 已集成部分
```

### 交付物定义
```
P0: 核心链路集成代码
P1: + 完整接口对接
P2: + 集成测试 + 监控
```

## 模式8：探索 (Explore)

### 适用场景
- 代码探索、架构分析、技术调研

### 循环策略
```
1. 宏观先行: 先了解整体结构，再深入细节
2. 问题驱动: 带着具体问题探索
3. 逐步深入: 广度优先 → 深度优先
4. 记录发现: 每个发现立即记录
```

### 验证标准
```
P0验证:
- 核心问题有答案
- 关键模块有理解记录

P1验证:
- 完整架构图
- 依赖关系清晰
- 关键流程有文档

P2验证:
- 深入到代码级别
- 性能热点识别
- 改进建议清单
```

### 降级方案
```
理想: 完整调研报告
降级1: 核心问题有答案 + 标注[待深入]
降级2: 宏观结构梳理 + 标注[待细化]
降级3: 初步发现记录 + 探索方向建议
```

### 交付物定义
```
P0: 调研报告（核心问题）
P1: + 架构图 + 依赖分析
P2: + 代码级分析 + 改进建议
```

## 模式自动识别

当用户未指定模式时，自动根据任务描述识别：

```python
def detect_mode(task: str) -> str:
    """自动识别任务模式"""
    
    dev_keywords = ["开发", "实现", "构建", "创建", "develop", "build", "create"]
    fix_keywords = ["修复", "解决", "排查", "fix", "debug", "resolve"]
    refactor_keywords = ["重构", "优化", "调整", "refactor", "optimize", "restructure"]
    test_keywords = ["测试", "覆盖", "test", "coverage", "quality"]
    doc_keywords = ["文档", "说明", "readme", "doc", "document"]
    iterate_keywords = ["迭代", "改进", "打磨", "iterate", "improve", "refine"]
    integrate_keywords = ["集成", "整合", "对接", "integrate", "connect"]
    explore_keywords = ["探索", "分析", "调研", "explore", "analyze", "investigate"]
    
    # 按优先级匹配
    for mode, keywords in [
        ("fix", fix_keywords),
        ("dev", dev_keywords),
        ("refactor", refactor_keywords),
        ("test", test_keywords),
        ("doc", doc_keywords),
        ("iterate", iterate_keywords),
        ("integrate", integrate_keywords),
        ("explore", explore_keywords),
    ]:
        if any(kw in task.lower() for kw in keywords):
            return mode
    
    # 默认: 开发模式
    return "dev"
```

## 模式切换

修仙过程中可动态切换模式：

```
场景: 开发过程中发现 Bug
→ 切换到 Fix 模式修复
→ 修复完成切回 Dev 模式

场景: 重构过程中需要先写测试
→ 切换到 Test 模式补充测试
→ 测试完成切回 Refactor 模式

切换规则:
- 切换时保存当前模式进度
- 切换后使用目标模式的验证标准
- 切换原因记录到决策日志
- 不需要用户确认（铁律二）
```
