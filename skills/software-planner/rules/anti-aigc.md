# 软件规划文档反AIGC检测规则

软件规划文档（需求描述、模块规格、README、架构设计）面临的AIGC检测不同于一般技术文档——它要求专业性，但不能是空洞的专业术语堆砌。好的软件规划读起来像架构师在白板前边画边讲，AI生成的读起来像模板填空，正确的但可以放在任何项目上。软件规划的反AIGC核心和技术架构文档一致：**具体**和**有决策理由**。

## 核心原则

软件规划反AIGC的关键是**需求可验证**和**设计有约束**。AI倾向生成"系统需要具备良好的用户体验"这类不可验证的需求。人类写软件规划会写"用户从启动到完成首次操作不超过3步"，会写具体的平台版本号、密钥长度、延迟上限。

## 软件规划AIGC高发模式

### 1. 技术选型无理由（权重25%）

```
❌ AI模式：
"使用Python作为后端语言，因其丰富的生态系统"
"采用Flask框架，因其轻量灵活"
"选择PostgreSQL，因其稳定可靠"

问题：这些理由放在任何项目上都成立，毫无针对性。

✅ 专业写法：
"后端选用Python 3.10+，核心考量是数据处理的numpy/pandas生态——本项目需处理百万级CSV的实时聚合，C扩展的numpy比纯JS实现快40倍。Flask而非Django，是因为本系统只需5个REST端点，Django的ORM和模板引擎是多余的3MB依赖。PostgreSQL而非MySQL，因为本系统需要JSONB字段存储非结构化配置，且需要事务性的DDL，MySQL 8.0之前的版本不支持。"
```

### 2. 需求描述空洞（权重20%）

```
❌ AI模式：
"系统需要具备良好的用户体验"
"支持多平台部署"
"保证数据安全"
"系统应具有高可扩展性"

问题：这些需求不可验证，无法判断是否满足。

✅ 专业写法：
"用户从启动到完成首次操作的步骤不超过3步（当前竞品平均5步，见竞品分析附录A）"
"支持Windows 10+（x64）、macOS 12+（x64/ARM64）、Ubuntu 22.04+（x64）。不支持：ARM Linux、32位系统、Chrome OS。命令行版本无平台限制（纯Python）。"
"数据传输使用TLS 1.3（不支持TLS 1.2以下），存储使用AES-256加密，密钥由系统管理员每90天轮换（密钥长度256bit，不允许硬编码在源码中）"
"扩展性目标：单实例支持200并发连接，超出需要水平扩展至2+实例（已有负载测试验证）。不追求：单实例1000+并发（需架构重写，ROI不合理）。"
```

### 3. 模块职责描述抽象（权重20%）

```
❌ AI模式：
"core模块负责核心业务逻辑"
"api模块提供外部接口"
"gui模块负责用户交互"

✅ 专业写法：
"core模块（约200行）实现数据聚合的3个步骤：读取CSV→按key分组→计算sum/avg/count。不依赖任何外部库——numpy、pandas都在api层引入，这样单文件运行时只需core+cli，不强制安装120MB的PySide6。api模块（约100行）封装core为5个REST端点：GET /status、POST /aggregate、GET /result/{id}、DELETE /result/{id}、GET /export/{format}。cli模块（约80行）是api的命令行薄层，1:1映射5个端点。gui模块（约150行）是api的PySide6界面层——gui可以被编译期排除（pip install package[cli]不含gui依赖）。"
```

### 4. 架构描述只有"模块化"（权重15%）

```
❌ AI模式：
"系统采用模块化设计，各模块职责明确，耦合度低"
"前端负责用户界面展示，后端负责业务逻辑处理，数据库负责数据存储"
"系统具有良好的可扩展性和可维护性"

✅ 专业写法：
"系统拆分为4个模块：core（数据聚合引擎，200行，0外部依赖）、api（REST接口，100行，依赖core+Flask）、cli（命令行入口，80行，依赖api）、gui（PySide6界面，150行，依赖api）。依赖方向：gui→api→core，cli→api→core。不允许反向依赖（core不import api的任何符号）。这样设计的效果：pip install package只安装core+cli（总大小2MB），pip install package[gui]才安装PySide6（额外120MB）。"
```

### 5. 规格参数模糊（权重10%）

```
❌ AI模式：
"系统性能优异"
"响应速度快"
"支持高并发"
"具有良好的用户体验"

✅ 专业写法：
"API端点p50延迟<50ms（本地测试，万条记录聚合），p99<200ms"
"单实例支持200并发连接，超出需要水平扩展至2+实例"
"GUI启动时间<2s（冷启动），界面切换<100ms"
"数据聚合：10万行CSV<5s，100万行CSV<30s（含磁盘IO）"
"内存占用：CLI模式<50MB，GUI模式<200MB（含PySide6运行时）"
```

### 6. 不标注不确定性和折衷（权重10%）

```
❌ AI模式：
全文语气确定，所有设计决策都像唯一正确答案。

✅ 专业写法：
"缓存策略选LRU而非LFU，因为本系统访问模式偏向最近热点（p90数据集中在最近1小时）。如果后续用户行为变为长尾分布，需要切换为LFU，但这需要额外2天开发。——这里选LRU是折衷，不是唯一解。"

"以下两个方案均可，A方案开发快（3天）但查询慢（200ms），B方案开发慢（7天）但查询快（20ms）。本版先选A方案上线，v2切到B方案。"

"GUI框架选PySide6而非Tkinter——理由：(1)本系统需要表格组件和图表组件，PySide6原生支持，Tkinter需要手动实现；(2)PySide6的样式表(CSS)支持比Tkinter强。折衷：PySide6安装包120MB，是本系统最大的依赖——如果用户只需要CLI，可以pip install package[cli]跳过GUI。"
```

## 软件规划反AIGC六原则

### 1. 每个技术选择标注排除理由

不写"选用X"，写"选用X因为[具体理由]，排除Y因为[具体理由]"。

### 2. 每个需求可验证

不写"良好的用户体验"，写"首次操作不超过3步"。

### 3. 每个模块有行数和依赖

不写"core模块负责核心逻辑"，写"core模块（200行，0外部依赖）实现3个步骤"。

### 4. 每个性能指标标注数字

不写"性能优异"，写"p50<50ms，p99<200ms"。

### 5. 不确定的地方明确标注

不写确定语气，写"此处有折衷"、"此处需后续验证"、"两个方案均可，选A是因为X"。

### 6. README避免营销语言

不写"强大的/灵活的/高效的"，写具体的输入输出样例和命令行用法。

## AIGC率检测清单

### 内容检测
- [ ] 每个技术选择是否标注了排除理由？→无理由=AI
- [ ] 需求描述是否可验证（有数字、平台版本、时间限制）？→不可验证=AI
- [ ] 模块描述是否可映射到代码结构（有行数、依赖方向）？→不可映射=AI
- [ ] 性能指标是否有具体数字？→无数字=AI
- [ ] 是否标注了不确定或折衷之处？→全确定=AI
- [ ] README是否有具体的命令行样例而非营销语言？→营销语言=AI

### 语言检测
- [ ] 是否出现"强大/灵活/高效/全面"等营销词？→出现≥3个=AI
- [ ] 是否出现"首先其次最后"机械递进？→有=AI
- [ ] 是否有量化指标而非定性描述？→定性=AI
- [ ] 技术选型理由是否适用于任何项目？→适用=AI
- [ ] 模块职责描述是否是万能的（"负责核心逻辑"）？→万能描述=AI

### AIGC率评分标准

- 0-15%：像资深架构师的设计文档，每个选择有数据支撑
- 16-30%：合格，有少量可优化项
- 31-50%：需修改，像模板填空
- 51-70%：需重写，空洞无实质
- 71-100%：纯AI模板，放到任何项目上都成立
