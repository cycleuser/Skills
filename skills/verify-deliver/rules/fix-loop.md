# 修复-重验循环 (Fix-Verify Loop)

校验发现问题的标准处理流程。

## 循环协议

```
发现 FAIL
  └─> 判断根因（打开失败/内容错/格式漂移/文件丢失/口径不符）
       └─> 修复（写新文件，或修脚本重跑）
            └─> 重新校验同一清单
                 └─> 仍 FAIL → 再修，最多 3 轮
                      └─> 3 轮仍 FAIL → 向用户报告根因与阻塞，不静默放弃
```

## 常见根因速查

| 现象 | 根因 | 修复 |
|------|------|------|
| docx 打开报损坏 | 改了 `[Content_Types].xml` 或删了单元格唯一段落 | 保留单元格至少一段；重做 |
| 合并单元格没填上 | 用逻辑坐标访问，实际是物理 tc 合并 | 按 `row.cells[i]` 实际返回的 tc 填，用 id 去重 |
| 数字不一致 | 多个来源未对齐 | 列出证据链，以用户确认口径为准，三处（表/正文/报告）统一 |
| 图片方向不对 | 90° 扫描 | OCR 盒坐标检测后旋转，quality=95 |
| 文件丢失 | 删除旧文件过早 | 新文件通过校验后才删旧 |

## 原则

1. 修一处验一处，不要攒一批再验。
2. 修复结果写新文件（`-edited` / 新路径），生产环境不覆盖原件。
3. 每轮修复记录在案，汇报时给出修复清单。
